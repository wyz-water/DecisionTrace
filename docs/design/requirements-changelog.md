# Requirements Change Log (SRS → Design)

Part II design document — DecisionTrace

**Status:** Draft for team review (2026-11-09; updated 2026-11-12)
**Baseline:** `docs/SRS/srs.md` (submitted 2026-10-23)

Every requirement change between the SRS baseline and the Part II design,
with its reason and evidence. The SRS itself stays untouched: this log is
the authoritative record of how the design evolved.

| # | Change | SRS baseline | Design decision | Reason | Evidence |
|---|---|---|---|---|---|
| C1 | Extraction runs automatically on file import | UC01 step 4: extraction is opt-in, default off | Importing a discussion triggers extraction immediately (rule engine by default; the LLM runs only when `DEEPSEEK_API_KEY` is configured, so the SRS privacy opt-in is retained for the LLM path) | Instructor feedback point 1: the human's job should be verifying, not transcribing | PR #20, #26 |
| C2 | Rationale (decision goal) required on manual creation | UC04: create a decision; fields not further constrained | `POST /decisions` rejects an empty rationale with 400; the create form requires it; revision may change but never erase the rationale. Decisions confirmed from candidates are exempt — their goal context is the source discussion | Instructor feedback point 0: decision goals must be explicit and recorded | PR #26, `fix/consistency` |
| C3 | Batch confirmation in the review queue | UC03: review each candidate one by one | Select-all-per-page + confirm-selected sends one request; per-item failures are reported; candidates flagged as duplicates are skipped by default (single confirm remains available) | Instructor feedback point 1: reduce review burden | PR #26 |
| C4 | Duplicate detection against authoritative records | UC02/UC03: extraction dedupes only against its own candidates | Pending candidates matching an existing decision / commitment / dependency carry `duplicate_of` (e.g. "Decision #3"), computed on read; title matching tolerates the extractor's cleaning ("Use Redis" ≡ "Redis") | Same fact re-stated in a meeting should not re-enter the trace unnoticed | PR #26 |
| C5 | Rule-based meeting summary on every discussion | Not in SRS (summary was implicit in the graph-snapshot idea, §2.3) | Every discussion response carries a computed summary (decisions / commitments / dependencies with names) from the rule engine only — offline, deterministic, never via the LLM; one click saves the current graph as the meeting snapshot | Instructor feedback point 1 + SRS core idea "meeting summary = graph snapshot" | PR #26 |
| C6 | What-if impact preview | UC07: impact is reported for actual DELAYED/BLOCKED states | New read-only endpoint `GET /commitments/{id}/what-if?status=DELAYED|BLOCKED` previews the hypothetical downstream closure, split into newly vs already affected; never writes a history row | UC07's "possible impact" made interactive without risk | PR #24 |
| C7 | Overdue highlighting | Commitment `due_date` is informational | Overview shows an attention entry and the plan view marks overdue commitments red | Demo feedback: due dates should be visible, not just stored | PR #21 |
| C8 | Discussion file import | UC01: paste a transcript or type a note | `.txt/.md/.docx/.pdf` import with drag & drop, UTF-8 with GBK fallback | The team's notes are mixed-format files | PR #20 |
| C9 | Bilingual UI (中文/EN) | SRS written in English; no language requirement | UI toggle with persisted preference; all strings via i18n | Team and course audience are Chinese-speaking; demo readability | PR #22 |
| C10 | Snapshot comparison | SRS §2.3: meeting summary as a graph (idea) | Snapshots are first-class (`POST/GET/DELETE`), with a structural diff between any two | Makes the "graph-structured meeting minutes" idea demonstrable | PR #21, #22 |
| C11 | Status-transition matrix deferred | UC05: "OPEN → IN_PROGRESS → …" implies a full transition rule set | Only the status vocabulary is enforced today; the explicit transition matrix (which jumps are legal) is deliberately deferred to Part III PoC validation | Honest scoping: rules need pilot data, not guesses | `docs/design/architecture.md` §11 R1, module-plan |
| C12 | Dependency editing deferred | UC06: create and inspect dependencies | Creation/removal implemented; editing an existing edge (change type/endpoints) deferred to Part III | Graph integrity checks made edit-by-edit safer to postpone | `docs/design/architecture.md` §11 R5, module-plan |
| C13 | Discussion text is the system of record | SRS §2.3: graph snapshot idea; minutes and graph both produced by the system | The uploaded/pasted discussion is the primary artifact; the graph is a derived view over it — every record links back to its source sentence; humans confirm/correct extraction, never maintain the graph by hand (A10) | Instructor follow-up critique (2026-11-12): manual entry made the tool "worse than meeting minutes" | `docs/design/architecture.md` §5, A10 |
| C14 | Natural-language ask view (planned, Part III) | Not in SRS | "What is blocking X?" answered from the derived graph with citations to source spans; rules answer first, the LLM may phrase but never invent (A11) | The trace should answer questions, not just store records — the missing half of "worse than minutes" | `docs/design/architecture.md` §5, A11 |
| C15 | Proactive alerts on the overview (planned, Part III) | SRS overview: KPIs and lists only | Overview surfaces what changed since the last visit without being asked: new conflicts, newly overdue commitments, decisions whose dependencies slipped | The system should speak first instead of waiting to be queried | `docs/design/architecture.md` §5 |
| C16 | Evaluation protocol formalised (Part III) | SRS §7.6: field accuracy ≥ 80% target only | §10 now defines: precision + recall per entity type, error taxonomy, blind rules-vs-LLM comparison with a pre-fixed adoption rule, summarisation coverage/faithfulness/snapshot metrics, verification-time experiment, and an end-to-end test against a hand-written-minutes baseline | Instructor: how the technical approach is evaluated, and how the evaluation is run, was not visible — it now is a protocol | `docs/design/architecture.md` §10 |
| C17 | Argument entity + deliberation layer | SRS: four concepts (Decision/Commitment/Dependency/Change); arguments only implicit in discussions | Fifth concept `Argument` (FOR/AGAINST, claim, author, target decision, source span) enters through the candidate gate; a decision with an open objection is **contested**, computed on read (never a manual status) | Instructor follow-up critique (2026-11-12): recording only conclusions throws away the reasoning — the high-level part of decision-making | `docs/design/architecture.md` §6, A12–A13; `docs/design/data-model.md` |
| C18 | Deliberation surfaces | Not in SRS | The layer is visible everywhere the trace is: a dedicated deliberation view (all arguments incl. free-standing, filters, resolve), overview attention entries for contested decisions, contested markers in the decision selector, and search coverage for claims/authors/stances | An argument confirmed but invisible would silently drop the dissenter's voice — the layer must be as browsable as the records it reasons about | `docs/design/architecture.md` §6; `docs/design/ui-design.md` |
| C19 | Decision health metrics (retrospective) | SRS overview: KPIs and lists only | `GET /projects/{id}/health` computes, on every read: overturn rate, average lifespan of overturned decisions, revision rate, contested rate, objection resolution rate — from the append-only history and the arguments (nothing stored); the overview shows them in a retrospective card; `Decision.created_at` added (records when a decision was recorded) | The "reflect" step of the agent loop; minutes can record words, not how the decision process performs | `docs/design/architecture.md` §5; `docs/design/api-spec.md` |
| C20 | Critical path analysis (planned, Part III) | SRS: topological order of the dependency graph only | Earliest/latest scheduling over the graph with due dates, surfacing the commitments actually on the critical path instead of every overdue one | Topological insight upgrade; scheduled for Part III PoC | `docs/design/architecture.md` §5 |
| C21 | Decision pre-check gate before confirmation | Not in SRS | Confirming a decision candidate first drafts counter-considerations from real sources: pending objections targeting it, concern sentences the extractor missed, an overturned precedent with a similar title, a missing rationale. Each needs a resolution reason; resolutions are recorded as resolved `AGAINST` arguments on the decision. Drafts are computed on read and recomputed at confirm time. | A ledger records what was said; an analyst also surfaces what was not addressed — the reframe's "analyst" made concrete (A14) | `docs/design/architecture.md` §5–§6, A14; `docs/design/api-spec.md` |
| C22 | Reversal trace for overturned decisions | SRS: decisions carry a status; no link between a decision and its replacement | `SUPERSEDED` can name the successor (`superseded_by_decision_id`); `GET /decisions/{id}/reversal` assembles the narrative — the flip row, the successor, the objections that accumulated, the linked commitments that slipped — every signal citing the row it came from; the decision card renders the timeline (EN/ZH) | "Why did this decision die?" is the most informative question about a decision, and the trace already holds the answer (A15) | `docs/design/architecture.md` §6, A15; `docs/design/data-model.md`; `docs/design/api-spec.md` |
| C23 | Severity-weighted impact cascade | SRS: what-if preview reports a flat downstream list | Effective severity propagates along `BLOCKS` edges: BLOCKED outranks DELAYED; a COMPLETED commitment is immune and isolates its downstream. The what-if response adds per-item baseline/simulated severity, blocked/delayed tier counts over the affected set, and the escalated ids; the impact panel ranks the cascade by severity then depth and shows Now-vs-If tiers (EN/ZH) | A flat "affected" list hides the difference between a slip and a stop; the topological foundation (A8) makes the cascade computable on read | `docs/design/architecture.md` §5, A16; `docs/design/api-spec.md` |
| C24 | Extraction sharpening | SRS: candidates carry no confidence; commitments link to decisions only by hand; natural-language due dates dropped | Every candidate carries an evidence-based confidence score computed on read (badge + "select high-confidence" batch pre-selection; never auto-confirms, A2). Commitments link to their context decision by proximity. Due phrases resolve to dates ("by Friday" → next Friday) and the original wording is always kept on the candidate — nothing silently dropped | Three cuts of the review burden at the extraction step: fewer clicks, fewer manual edits, fewer lookups | `docs/design/architecture.md` §5, A17; `docs/design/api-spec.md` |
| C25 | Decision layer: makers and decision-to-decision edges | SRS: decisions carry no maker; the graph has only commitment-level dependencies; no stakeholder view | Decisions record `decided_by` (named-person patterns EN+ZH; "we decided" stays a team decision); `DECISION_DEPENDENCY` candidates ("…after we had decided to…" / "building on our decision to…") enter through the candidate gate with duplicate/self/cycle rejection on the decision graph; the reversal trace gains a "resting decisions" signal; `GET /projects/{id}/stakeholder` + the overview panel answer the decision-maker's questions: do my decisions still stand, what does my work rest on, who waits on me | The instructor's first critique was that decision-maker and decision-goal analysis was weak (architecture §2); the decision layer is the structural answer — who decides and what decisions rest on what | `docs/design/architecture.md` §2/§5, A18; `docs/design/data-model.md`; `docs/design/api-spec.md` |

Unchanged from SRS: the four core concepts, the candidate gate (A2 /
UC02–UC03), cycle refusal before storage, the append-only history tables,
and the AI autonomy boundaries of §7.6.
