# DecisionTrace 重新定位设计草案

> 状态:讨论稿 — 供团队确认、与导师沟通后,再决定代码改动顺序。
> 本文档尚未对项目做任何修改。

## 0. 背景:导师两次反馈的收敛

1. 「选题和切入点很高级,但形式让它显得低级、不够好用」— 产品陷在局部功能里。
2. 「最主要的是 DecisionTrace 为了什么、服务于谁、连接哪些系统、哪些决策值得提取」— 要求先回答系统级的问题,而不是堆功能;并点名质疑:列未回应的疑问是否真有用、「像一个项目吵架的 storyboard」、「现在更像项目进度展示」。

本草案是对这两次反馈的系统性回应。

## 1. 定位

**定位句:决策透明是高质量监督与指导的基础。**

DecisionTrace 是一个服务于**导师(一)与学员项目组(多)**之间的决策透明层:

- 学员在系统里**记录和讨论决策**,形成一条条决策链;
- 导师**看到每个组的决策是什么、谁做的、进展如何**,并批注、认可、否决或挂起;
- 决策被认可后才进入执行阶段,执行进度双方共享。

**决策与项目的关系(本设计的理论前提):**

- 项目 = 容器 + 执行流(任务、进度、资源);
- 决策 = 方向上的承诺点(在可选方向中做出有约束力的选择);
- 决策属于项目,但不是项目任务:任务完成即结束,决策持续约束未来,直到被推翻;
- 比喻:执行是划桨,决策是掌舵。**导师监督的是舵,不是桨。** 周报汇报桨,DecisionTrace 记录舵。

**服务于谁:**

| 角色 | 他问什么 | 系统给什么 |
|---|---|---|
| 导师(主) | 各组做了什么决策、为什么、谁做的、进展如何 | 按组决策看板 + 批注 + 执行进度 |
| 学员(次) | 被询问时有迹可循;自己的工作不丢上下文 | 决策链记录 + 按人审核 + 执行顺序 |

## 2. 系统全貌

```
学生端                              导师端
┌────────────────────────┐
│ ① 决策采集             │
│  会议文本 + AI 提取     │
│  按决策人颜色标注       │
│  各自审核自己的部分     │
│  手动补充非会议决策     │
└──────────┬─────────────┘
           ▼
┌────────────────────────┐           ┌──────────────────────────┐
│ ② 决策链               │──提交──▶  │ 按组看板:待处理的链      │
│  最新节点下群聊式讨论   │           │ 认可 / 否定 / 待定 + 批注 │
│  达成一致 → 追加新节点  │◀─回传──── │ (批注是一等动作)         │
│  (推翻 = 新节点)       │           └──────────┬───────────────┘
└──────────┬─────────────┘                      │ 认可
           ▼                                   ▼
┌────────────────────────┐           ┌──────────────────────────┐
│ ③ 执行监督             │           │ 执行进度(复用学生端视图)  │
│  任务来自链上讨论       │──进度──▶  │ 导师只读                 │
│  拓扑排序安排顺序       │           │ 干预仍走链上批注         │
│  AI 检查顺序/卡点/成环  │           │                          │
└────────────────────────┘           └──────────────────────────┘
```

两个闭环:**审阅闭环**(提交 → 批注 → 修订 → 再提交)与**执行闭环**(认可 → 执行 → 进度可见)。

## 3. 学生端三大功能

### 功能一:决策采集

- 粘贴会议讨论文本,AI 提取决策点并**锚定原文句子**;
- 页面按**决策人颜色**标注:每人固定一种颜色,「我们决定」的集体决策用中性色(由讨论提交人负责审核);
- **谁说谁审**:每个决策人只核对自己说过的话(确认/修改)— AI 不确定性的保证机制 = 责任到人的简单人工审核;
- 手动提交决策:不是所有决策都发生在会议上,提供独立入口。

### 功能二:决策链

- **链 = 一个主题的决策演进过程**:节点(决策版本)+ 节点下的讨论;
- **讨论统一化**:疑问、反对全部合并为「讨论」,群聊式留言,任何人可在最新节点下发言 — 没有 FOR/AGAINST 分类、没有 contested 状态、没有解决仪式;
- 达成一致后**追加新节点**延长链路;**推翻就是链上的新节点**(如「用 Redis」→「改用 Memcached」);
- 讨论记录与决策节点严格绑定,留作追踪记录;
- 挂链方式:手动把新决策挂到已有链或开新链,不做自动聚类;
- **提交导师是唯一的门**:组员判断链已成熟即可提交;提交不冻结,可继续讨论、加节点、重新提交。

### 功能三:执行监督(导师认可后启动)

- 任务来自链上讨论中自然产生的「谁做什么」,不另设任务录入;
- **拓扑排序**安排执行顺序(人和任务绑定);
- **AI 监督执行**:检查顺序错误、卡点、依赖成环;
- 进度视图双方共享。

## 4. 导师端

### 决策敲定(链的审阅)

- 界面**按组划分**,只看到学生**已提交**的链;
- 动作集:**认可 / 否定 / 待定 + 批注**;
  - 批注是一等动作:可独立于三态(只批注不表态合法),任何三态都可附批注;
  - **待定 = 已阅,挂起待议**(如组会当面讨论),与「还没看」区分;
  - **否定不删链**:否定只是链历史中的一个批注节点,组员继续讨论、追加新节点、重新提交;
- 回传闭环:学生提交 → 导师端该组出现「待处理」标记;导师批注 → 学生端该链出现「导师有回复」标记(双侧各一个未读徽章)。

### 执行进度

- 复用学生端进度视图,**导师只读**;
- 执行期间导师想干预,回到链上批注 — 进度视图上不另设干预入口,保持导师端三件事:看链、批注、看进度。

## 5. 现有功能去向表

| 现有功能 | 去向 |
|---|---|
| decided_by 抽取 + span 锚定 | **功能一核心**(颜色标注、按人审核) |
| 手动创建决策 | **功能一**(非会议决策入口) |
| 决策依赖、推翻关系 | **功能二的链结构**(推翻 = 新节点) |
| 论点 / contested / 解决仪式 | **退役** → 统一为链节点下的群聊式讨论 |
| 预检门、逐条挑战 | **移除**(唯一门 = 提交导师) |
| 承诺 / 依赖 / 状态机 / 拓扑排序 / 成环检测 | **功能三 + 导师端执行进度**(确认后的下游,双方共享) |
| 严重度级联 / what-if | 收缩为执行进度的辅助提示,或暂缓 |
| 决策健康指标 | 导师端轻量统计(每组一行) |
| 项目切换器 | 升级为**导师端按组视图**的基础 |
| 翻案追溯 | 保留 — 导师看链的演变正需要它 |

## 6. 数据模型变化(草案)

- **决策链**:先作为轻实体(名称 + 主题决策),节点 = 决策版本(沿用决策 + 版本历史,推翻即新版本);链的合并/拆分由组员手动挂接;
- **讨论留言**:替代 Argument 实体,挂在链的节点下;
- **提交与导师状态**:链上增加 `submitted_at`、导师状态(待处理/认可/否定/待定)、批注列表;
- **执行任务**:轻量(负责人 + 描述 + 依赖 + 状态),来自链上讨论,拓扑排序与 AI 检查在读取时计算。

## 7. 演示故事(导师视角)

1. **学生端**:粘贴会议记录 → AI 按人标色提取决策点 → 各自确认自己的部分 → 手动补一条会外决策 → 在链下讨论 → 达成一致后追加新节点 → 提交导师;
2. **导师端**:按组看板出现新链 → 打开看决策、决策人、讨论 → 批注「补充成本对比」+ 待定 → 回传;
3. **学生端**:看到导师批注 → 继续讨论 → 追加新节点 → 重新提交;
4. **导师端**:认可 → 执行阶段开始 → 任务按拓扑顺序排开,AI 检查执行 → 导师看实时进度。

现有演示数据(Alice 的决策、Bob 的反对、Redis 被 Memcached 取代、Carol 卡住)几乎可直接映射到这个故事的每一步。

## 8. 待定的小问题

1. 集体决策(「我们决定」)的颜色与审核归属:草案为中性色 + 讨论提交人审核;
2. 执行视图的单位:每条链一份执行计划,还是每组一个聚合执行板(草案:先每链,聚合后议);
3. 未读/通知机制的实现深度(徽章即可,还是需要站内消息列表)。
